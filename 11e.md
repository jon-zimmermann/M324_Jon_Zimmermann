## How GitHub Pages works

GitHub Pages hosts static files (HTML, CSS, JavaScript, images) straight from a repository. Nothing runs on a server; GitHub just delivers the files. There are two ways to publish:

1. **Deploy from a branch:** pick a branch and folder (e.g. `main` / root). Every push to that branch starts the built-in workflow *pages build and deployment*.
2. **GitHub Actions:** your own workflow builds the site, uploads it as an artifact and deploys it with `actions/deploy-pages`. This gives you full control over *when* and *what* gets deployed.

With a free account, Pages only works for public repositories. The URL is `https://<user>.github.io/<repository>/`.

### Let's assume your app needs a database. How could you do that?

GitHub Pages can only serve static files. There is no server where a database or backend code could run. So there are a few options:

1. **Store data in the browser:** `localStorage` or `IndexedDB`. My game already does this for the best score. This is fine for data that only matters to one user on one device, but it can't be shared (e.g. no global leaderboard).
2. **Backend-as-a-Service:** services like **Supabase** (PostgreSQL), **Firebase / Firestore** or **Cloudflare D1** offer a database with an HTTP API that the JavaScript in the browser can call directly. Only a public key goes into the frontend; access is restricted with rules on the database side (e.g. Row Level Security in Supabase), because everything in a static site is visible to everyone.
3. **Own backend:** write a small API (e.g. Flask in a Docker container, or a serverless function like AWS Lambda or a Cloudflare Worker) that talks to a database (e.g. AWS RDS, PostgreSQL). The Pages site calls this API with `fetch()`. This is more work but gives full control, and secrets (database password) stay on the server.

Important in every case: **never put database passwords or secret keys into the repository or the HTML**. The repository is public and the website code can be read by anyone. Secrets belong in GitHub Actions secrets or on the backend.

For a leaderboard for my game I would use option 2 (Supabase), since it needs no own server and has a free tier.

### Deploy only when a new tag is pushed – is this possible?

**Yes, it is possible.** The built-in "Deploy from a branch" mode can't do it, because it deploys on every push to the chosen branch. So I switched to a custom GitHub Actions workflow.

What I did:

1. **Settings → Pages → Build and deployment → Source:** changed from "Deploy from a branch" to **GitHub Actions**. This turns off the automatic *pages build and deployment* workflow on every push.
2. Created `.github/workflows/pages.yml` that only triggers on tags:

   ```yaml
   on:
     push:
       tags:
         - "v*.*.*"
     workflow_dispatch:
   ```

   There is no `branches:` trigger, so a normal commit on `main` does not start the workflow. `workflow_dispatch` only lets me start it manually as a fallback.
3. The workflow has two jobs:
   - `build`: checks out the tagged commit, copies `index.html` into `_site/`, writes the tag name into the page (`sed` replaces `{{VERSION}}` with `$GITHUB_REF_NAME`) and uploads the folder with `actions/upload-pages-artifact`.
   - `deploy`: publishes the artifact with `actions/deploy-pages` into the `github-pages` environment.
4. **Settings → Environments → github-pages → Deployment branches and tags:** added the tag rule `v*`. By default this environment only allows deployments from the default branch, so without this rule GitHub blocks the tag deployment ("Tag ... is not allowed to deploy to github-pages due to environment protection rules").

How to test it:

- Push a commit to `main` → no workflow run in the Actions tab, website stays the same.
- Create a new release with a new tag (e.g. `v1.1.0`) on GitHub, or run `git tag v1.1.0 && git push origin v1.1.0` → the workflow starts and the new version is online after about a minute. The version in the footer changes to the new tag.

This is basically how release-based deployment works in real projects: `main` can contain unfinished work, and only a tagged, released version goes to production.
